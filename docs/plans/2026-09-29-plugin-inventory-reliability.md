# Codex Director：安装插件清单可靠性修复计划

## 目标与边界

修复升级后“安装插件”长期显示待核实的问题，同时保持数据诚实：只有确定取得完整的当前安装清单，才显示确定数量（包括真正的 0）；任何部分结果、协议错误或读取失败都不得覆盖上次可信清单，也不得让能力包的 `plugins.json` 声称完整。

本轮只调整插件发现、插件衍生 Skill 的可信状态及能力包插件列表。不修改插件安装状态、Codex 配置、账号凭证、能力源文件、其他索引器或自动刷新周期。不因这项修复主动推送 GitHub。

## 已确认原因与设计决策

- 当前 `CodexRuntimeDiscovery` 与能力包导出分别调用 `codex plugin list --json`。该 CLI 在远端 marketplace 获取失败时可能打印 warning、返回成功退出码并继续输出缺少远端项的 JSON。现有 stderr 防护避免了假完整，但只能持续显示“待核实”。
- Codex app-server 提供只读 `plugin/installed`，响应含 `marketplaces` 和 `marketplaceLoadErrors`，插件项含规范 `id`、`installed`、`enabled`。选它作为首选清单来源；不用 `plugin/list` 的可安装目录代替安装清单，也不把同名、不同 marketplace 的插件合并。
- `plugin/installed` 的响应结构本身并未提供一个覆盖所有远端来源的单独 `complete: true` 标志。正式实现前必须用当前 Codex 运行时验证失败语义；不能仅凭 JSON 可解析或 `marketplaceLoadErrors` 为空就假定远端源完整。

其他方案及结论：直接接受 CLI 的成功 JSON 会漏报；直接遍历插件缓存会把旧版本、未安装包算进去；两者都不能成为完整性事实源。CLI 可以保留为兼容诊断或受限回退，但若无法证明包含账户侧插件，就只能产生“部分/待核实”状态。

## 执行步骤

### 1. 先确认协议与当前运行时

1. 使用现有 Codex 可执行文件，以固定参数启动短生命周期 `app-server --listen stdio://`；初始化后仅调用 `plugin/installed`，不调用安装、卸载或 reconcile 方法，不传项目路径或安装建议。
2. 诊断仅输出结果分类与计数：运行时版本、marketplace 数量、安装项数量、错误数量、是否超时。不得打印或保存原始 JSON、账号元数据、绝对路径、插件正文。
3. 用合成服务响应检验：成功的空清单、远端失败、marketplace 部分加载、协议不支持、超时、取消、超量输出。对当前运行时做一次与 Codex 自身插件界面的人工只读对照。
4. 决策门：若无法分辨“远端确实没有插件”与“远端读取失败却返回空”，不将该结果升级为完整状态；继续显示待核实，并记录固定错误码供重试。不能为消除待核实而放宽真实性条件。

### 2. 建立单一的只读插件清单接口

1. 在 `DirectorCore` 增加可注入的插件清单读取器，复用现有 app-server 进程交换的超时、取消、输出上限和直接启动约束；不使用 Shell，不读取或保存凭证。只在现有源刷新或用户手动刷新时启动，不新建轮询器或第二套索引器。
2. 将响应投影为最小、隐私安全的数据：规范插件 ID（含 marketplace）、名称、版本、已安装/启用状态、已验证的本地包路径，以及完整性状态。丢弃远端插件 ID、账号、分享信息、原始错误消息和不需要的元数据。
3. 相同规范 ID 的重复项按明确规则去重；同名但 marketplace 不同的项独立保留。无效 ID、字段缺失或矛盾状态不能静默跳过后宣称完整。
4. 对 `marketplaceLoadErrors`、不完整远端读取、协议不兼容、超时与取消给出不同固定错误码；错误只影响插件域，不阻断已成功的本地 Agent/Skill 索引。只有经验证的完整响应才能将插件数量更新为确定值。

### 3. 接入发现、缓存与能力包

1. `CodexRuntimeDiscovery` 改用单一插件清单接口；保留现有“读取失败则保持上次有效插件及子能力，并标记未验证”行为。校验任何本地路径处于批准的源根内且符号链接不越界后，才扫描插件提供的 Skill、App、MCP 与 Hook。
2. 远端项没有可验证本地包路径时，仍可显示已安装插件身份；其子 Skill 数量保持未知或上次观察值并标记未验证，不能推断为 0。若需补齐子 Skill，优先使用一次批量、可归属插件 ID 的只读接口，而不是每个插件启动一个进程。
3. `RuntimeCapabilityPluginInventoryProvider` 与界面使用同一读取结果和完整性判定。能力包中的插件列表仍只记录元数据、不复制插件文件；不完整时 `plugins.json` 必须标明 `incomplete`。
4. 保持既有缓存/schema 的兼容读取。若规范 ID 替换了名称型资源 ID，先定义受控映射和去重回归测试，避免已保存的插件行、评价或关系出现静默重复；不清空真实数据。

### 4. 验证与交付

- 单元测试：握手及 `plugin/installed` 响应、明确空列表、部分 marketplace 错误、远端失败、旧运行时、超时/取消/输出上限、无效字段、同名不同 marketplace、显式禁用、路径越界。
- 集成测试：完整读取更新清单；失败保留上次有效值；插件子 Skill 不误清零；插件域失败不影响其他索引；主窗口、首页数量与能力包 `plugins.json` 使用相同可信状态；多窗口刷新合并。
- 隐私/性能：合成 fixture 不含真实账号或路径；日志、缓存和导出没有原始响应；未触发刷新时不启动插件进程；主线程无阻塞。
- 执行 `swift test`、`./scripts/verify.sh`、`./scripts/audit-public-release.sh` 和 Release 构建。通过后按项目安装规则覆盖安装并验证实际运行。若运行时完整性门仍未通过，则报告“待核实”的外部原因，不宣称修复完成。

## 验收标准

1. 当前 Codex 可正常提供完整清单时，安装插件页和首页显示与 Codex 当前安装项一致的数量；显式空清单才显示 `0`。
2. 任何远端失败、协议异常或部分清单都不显示伪造的确定数量；旧值可留存但明确标注“上次观察、待核实”，可手动重试。
3. 插件提供的 Skill 不因无本地包路径或一次接口故障被清零；能力包插件状态与界面一致。
4. 不修改 Codex 插件、配置或登录状态；不增加后台轮询；其他 Agent、Skill、额度和本地索引继续正常工作。

## 决策记录

状态：已在本地实现并验证，尚未提交或推送。当前安装包仍标记为 `1.4.0 (27)`；正式修复版本号与发布操作另行决定。生产路径改为 app-server `plugin/installed`。本机只读协议探测与覆盖安装后的界面刷新均显示 17 个安装项，且运行时返回一个远端 marketplace、零个显式加载错误；完整 Swift 测试、`verify.sh`、公共审计和双架构 Release 构建通过。远端插件没有可验证的本地包路径时，插件身份可计数，但其子 Skill 仍明确显示待核实。协议没有全局完整性证明，当前实现用远端 marketplace 见证作为保守门槛；远端缓存的新鲜度无法由此证明，不声称实时同步或其他账户环境均已验证。
